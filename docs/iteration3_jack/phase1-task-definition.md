## 1. 候选比较与人工决策

| 候选 | 产品价值 | 问题证据 | 架构实践价值 | 复杂度/验证难度 |
| --- | --- | --- | --- | --- |
| 1. 有目标的章节复习闭环 | 帮助学生判断覆盖、薄弱点和下一步 | 局部自测契约已确认；实际学习收益待体验 | 学习目标、状态与反馈契约 | 中等；需学习任务和未见题评价 |

**人工决策：选择候选2。** Codex 在 Task 2 曾优先建议候选1；用户在本次收尾指令中明确选择候选2，此次明确决策作为最终依据。选择理由：有具体运行证据，直接影响真实设计需求的课程支持；可形成来源质量前后对比，且能在现有系统内开展有边界的架构权衡。不是因为已证明某种新检索技术必要。

候选1、3延后为后续迭代待办，不属于本轮实施承诺。

## 2. 唯一主任务

**改善自然语言软件设计需求到课程知识来源的匹配与支持能力。**

- **用户场景：** 本科生在架构实践输入真实系统、负载、故障容忍和业务约束，尚不能准确表达质量属性和战术术语。
- **问题陈述：** 当前直接拼接输入并词法检索，可能遗漏需求隐含的相关架构知识；非空来源也可能不充分，后续分析因此缺乏合适课程依据。当前已验证一个对照例，不推广为所有输入失败。
- **目标：** 更有效地选择、组织真实且可追溯的课程知识，并供给后续架构分析。目标是匹配与证据供给，不是全面提高模型生成质量。
- **主要模块：** `DesignStudio.tsx`、`api.ts`、`server/models.py`、`main.py`、`design.py`；视已确认方案可能局部涉及 `search.py`、`retrieval_terms.py`、`chapters.py`。这是影响面，不是修改清单。
- **质量属性：** 功能适用性、来源正确性与覆盖、可追溯性、可修改性、性能、可靠性；安全边界和本地状态保护继续遵守。

## 3. 范围边界

### In Scope

1. 架构实践自然需求输入及其必要的澄清/提示调整。
2. 需求到课程知识的匹配、来源选择与组织。
3. 来源进入场景分析、战术、评审上下文的路径与契约。
4. 必要的局部接口、状态、测试和交互调整。
5. 自然需求来源质量评估、前后对比和代价记录。

### Out of Scope

- 完整智能学习路径、整章复习和自测体系重做。
- 全面 RAG 重构、全面替换检索技术或改造所有 AI 功能。
- 预设向量数据库、Embedding、新 Agent 框架或其他技术路线。
- 泛化为全面提升模型回答质量，或新增无关复杂功能。
- 无证据的共用模块改造；确需局部共用调整时，应说明必要性、影响面并做回归。

Phase 2 比较方案后由人工选择；新增超范围事项须单独说明并由人工决定。

## 4. 初始验收标准

以下为验收要求，不是已完成结果。自然需求评估集、耗时及成本等缺少基线的部分，均须在 **Phase 2 方案确认前建立**；阈值与取舍依据应经人工确认，不能到实现后按结果降低标准。

### A. 产品行为

- A1：对约定的自然设计需求案例，实际来源包含人工预先判定的相关知识；在线考试案例应有可用性相关依据。不强求所有正确答案都引用单一固定页。
- A2：所选 `(chapterId, slide)` 可定位到真实课件，摘录与实际内容对应，保留正文/备注/OCR来源差异，不捏造缺失内容。
- A3：通过捕获真实构造的模型请求，证明相关来源进入适用的后续分析阶段；检查重检索后是否丢失关键依据。替身只验证数据流，不替代内容质量评估。
- A4：场景 → 战术 → 评审、来源查看、草稿恢复、过期提示及导出继续可用；失败与取消不意外丢失输入/旧成果。
- A5：对于证据不足或存在歧义的输入，记录系统实际行为并按选定方案验证处理边界，不以无关来源充数冒充可靠支持。

### B. 来源质量

- B1：建立多场景自然需求固定集，至少涉及可用性、性能、可修改性，并包含多属性、歧义或资料不足案例；保留术语对照。案例数量与分布在 Phase 2 方案确认前确定。
- B2：在开发前确定每例预期知识、相关页集合及允许的替代页；人工核对课件。区分直接支持、背景相关、无关，并保存判断理由和争议处理，不按当前排名反向挑期望页。
- B3：固定返回预算和语料条件，分别记录相关来源比例、预期知识覆盖、无关来源数量及关键知识遗漏；多余/重复页不得虚增覆盖。
- B4：建立修改前逐例基线，之后使用相同输入、语料和规则比较。目标案例应改善，其他属性和保留案例不得出现未经说明和人工接受的退化。量化门槛在取得基线后确认，不虚构提升百分比。
- B5：预先划分一部分案例为保留验证集，不用于规则调试；实现稳定后评估。若用于调试，必须披露并补充新的未见案例，不能继续声称它是独立验证。
- B6：既有20条术语集用于兼容性回归；其16/20结果不是本轮自然需求质量基线。新评估与新结果单独保存，不改写旧集、旧结果。

### C. 架构质量

- C1：明确需求转换、检索、来源组织、上下文构建和模型生成的责任与契约；具体划分由方案比较决定。
- C2：保留模块化单体与既有配置、结构、引用、资料不可信和状态保护约束；不因指标需要绕过校验。
- C3：新增依赖、外部调用、缓存或持久化必须说明必要性、代价和替代方案；不引入不必要复杂度。
- C4：保留500行检查及相关接口/引用符合性验证；若修改共享检索，检查搜索、问答、自测的影响，按风险选择回归范围。

### D. 回归与验证

- D1：现有受影响测试通过，新增有针对性的需求匹配、上下文和引用回归；按最终影响面执行后端、前端、构建、行数与浏览器检查。不能以本地单测替代真实交互验收。
- D2：保存基线与改进结果、命令、commit/工作区、语料/OCR条件、配置和标注规则；主要结果可复算，失败及退化案例一并呈现。
- D3：本机浏览器优先Chrome。已有Chrome E2E通过记录不等于真实后端/模型链路通过；需要一条代表性的实践端到端验收记录。
- D4：真实模型验证使用授权配置，记录模型、时间、输入、来源与人工核对结论，保护凭据。替身验证与真实效果分开；不可用时记录阻碍与未完成范围，不能宣称已验收真实教学效果。
- D5：记录来源选择耗时、外部调用数/费用（如有）、上下文大小、依赖和维护复杂度变化。测量条件、重复方式及可接受代价在 Phase 2 确定，当前没有可引用数值。

## 5. Definition of Done

- [ ] 人工确认具体方案、架构约束和验收口径。
- [ ] 自然需求匹配与课程证据供给改进完成，未扩展到无关候选。
- [ ] 有开发前基线、修改后比较、保留集结果及失败/退化分析。
- [ ] 关键回归、新增针对性测试与代表性产品验收完成；限制如实列出，未完成项不冒充完成。
- [ ] AI结构与引用校验、真实课件溯源、失败保护及必要符合性检查保留。
- [ ] 架构方案、替代方案、人工选择、ADR及实际代价均有记录。
- [ ] Codex实现遵守已确认约束，例外与偏差有记录和处理结论。
- [ ] 文档、代码、命令及结果一致；真实模型验证状态清楚。
- [ ] Phase 4形成复盘、可复算证据索引及交接材料，保存在统一根目录。

未满足验收时记录差距，由人工决定后续，不以“功能可调用”替代任务完成。

## 6. Phase 2 输入与待决事项

输入为本任务定义、[基线与复现](phase1-baseline.md)、现有检索/实践代码和测试。下一阶段需要：

1. 进一步定位查询词、排序、上下文预算及分阶段协作的作用；建立质量属性场景。
2. 建立自然需求固定集、人工来源判定与保留集，以及性能/代价基线。
3. 比较架构方案，包括简单局部方案与可能需要额外推理的方案；评价收益、故障点、成本与共用影响，不提前选技术。
4. 人工选择方案并确定验收阈值，形成真实时点的ADR。
5. 输出 Coding Agent 开发约束：允许修改边界、接口、不变量、符合性检查与禁止事项。
6. 细化自动测试、来源评估、浏览器和真实模型验证计划。

Phase 3才在这些约束下实施与验证；Phase 4复盘架构符合性、权衡结果和AI协作过程并交接。Phase 1至此停止，等待人工检查。
