# 架构实践教学方式：理念、学习目标与问题设计

**用途：**记录 MAGA 架构实践 v2 的教学设计思想。技术接口、状态和代码结构请另读 [practice-architecture.md](practice-architecture.md)；原始“先设计、后编码”的实施契约见 [architecture-practice-v2.md](architecture-practice-v2.md)。

## 1. 为什么放弃“先写宽泛场景、让 AI 生成方案”

旧版要求学习者填写标题、场景描述、需求约束，然后让 LLM 按“质量属性场景 → 架构战术 → 评审”输出结果。存在三类教学偏差：

1. **起点太宽泛**：缺少项目背景和可供权衡的约束，初学者难以填写，输入质量成为主要门槛。
2. **关键思考被模型代做**：模型负责提出问题、选择技术战术、给出方案，学习者缺少必须解释自己的设计选择的环节。
3. **很难评估能力**：一份看似完整的模型输出，不足以证明学习者理解并发一致性、系统可靠性、模块协作、性能瓶颈与架构演进。

本轮的核心转向是**案例驱动的架构决策训练**：不要求画全套结构图、不设计完整接口契约、更不要求写实现代码；而是围绕项目开发中少数最重要的设计问题，要求学习者提出可辩护的方案、识别风险、比较替代策略并讨论优化。

**成功的学习不是选中了某个指定技术名词，而是能解释“为什么这个约束下适用”“有什么代价”“什么条件改变后需要调整”。**

## 2. 学习目标与能力范围

建议对一个案例评价以下五种能力，而不是一个无法解释的总分：

| 能力 | 证据来源 | 不应误判为掌握 |
| --- | --- | --- |
| 需求识别与约束分析 | 学习者自主指出关键业务不变量、性能/资源限制、未知条件 | 重述项目给定的需求文字 |
| 架构决策合理性 | 方案是否满足约束，有无关键故障/边界条件 | 只说“使用 Redis”“上微服务”等技术名称 |
| 方案论证与权衡 | 能否比较备选设计与代价 | 只给唯一结论、不给理由 |
| 故障与演进思维 | 面对异常或需求改变能否修订方案 | 把无限叠加组件当成通用解法 |
| 独立思考与反思 | 首次回答、追问后修正的差异 | 被 AI 提示后复述正确答案却算作完全独立掌握 |

阶段一的需求分析在 2026-11-24 调整为**推荐填写但可跳过**：用户选好案例后可直接开始。被跳过的阶段不能被模型伪装成“学生已完成需求分析”。这解决入门摩擦，同时保留填写者的额外分析证据。

## 3. 案例应如何设计

案例**模拟真实工程任务**，但并不声称是某公司或高校的真实生产项目。每个案例包含：
- 业务背景、核心操作、参与方；
- 明确功能需求、数据处理和业务不变量；
- 初始硬约束：规模、时延、可用性、团队和交付周期；
- 三个**预先设定但不提前给学生看答案**的架构决策目标与评价要点；
- 允许存在合理的不同方案，且需要识别尚未给定的条件。

已提供三个案例，见 `server/practice_cases.py`：

| 案例 | 关键问题 1 | 关键问题 2 | 关键问题 3 |
| --- | --- | --- | --- |
| 校园活动报名 | 名额不超卖与唯一报名；权威数据源和事务 | 报名、候补、通知的职责与可靠事件 | 高并发瓶颈、排队与响应语义、是否拆服务 |
| 高校在线考试 | 自动保存、重试和交卷幂等 | 网络/服务故障时保持考试状态与恢复 | 集中流量、扩容、背压与指标 |
| 图片素材检索 | 上传、GPU 特征抽取、异步索引流水线 | 原始元数据与向量索引的状态一致性 | 推理/检索性能、限流与分离部署 |

例如“选择 Redis 还是数据库事务”并没有永恒标准答案；如果学习者能指出跨存储一致性风险、热点锁竞争和测试前提，即体现比单纯套用战术更有价值的分析能力。

## 4. 学习过程与每一阶段的教学责任

`案例阅读 → 自主需求理解（可跳过） → 3 个关键决策问题 → 逐点回答与有限追问 → 综合评审 / 参考设计`。

### 阶段 A：案例与需求

展示**确定的背景和约束**，确保学生不是凭空编写业务。提出引导问题：影响架构的核心需求、业务不变量、待确认的限制与潜在风险。答复作为后续提问上下文，但不是参与资格门槛。

### 阶段 B：从需求中选出值得问的问题

系统使用预设考察目标控制范围，LLM 根据案例及用户已有分析**表述一个具体决策问题**。每个案例固定三点，避免无限扩展或遗漏教学目标。题目应提出一个需要作出选择的工程困难，而不是直接暗示答案或罗列技术清单。

本阶段课程检索的作用：**选择相关质量属性、战术、架构风格与权衡材料，以校准问题深度**；不是把课件答案直接贴给学生。

### 阶段 C：学习者独立回答、LLM 针对性追问

首次回答记录学习者自己提出的方案及理由。LLM 对回答中**最影响方案正确性的漏洞**追问，例如一致性窗口、失败补偿、幂等、可用性或验收指标。每个决策点最多追问两轮，避免无边界讨论和反复提示。

课程检索的作用：补充当前问题/用户方案涉及的课程概念，让追问有依据。追问应集中于**设计约束与边界条件**，不提前抛出完整参考实现。

### 阶段 D：逐点形成性反馈

模型指出已解决的问题、尚存的设计风险、方案取舍以及下一步思考方向。记录学生初次观点与追问后变化，不应将模型给出的修正提示全部计入独立能力。

课程检索的作用：为课程中明确给出的概念性判断提供真实页面证据；课程没讲过的工程推断应明确为“基于案例的分析”。

**当前实现中的反馈由 Answer 阶段一并产生**，不是额外单独发起一个独立“评分 API”。

### 阶段 E：综合评审与参考思路

全部三点完成后，模型基于所有首次答案、追问与完成状态给出：
- 总体评价：已表现出的设计理解与决策能力；
- 优势及其对应的回答证据；
- 需要进一步优化的关键点及验证前提；
- 供对照的一套或多套可行参考思路（不是唯一答案）。

课程检索的作用：为综合权衡和通用架构原则提供知识依据。不要因为课件中出现某种战术，就把它当成案例必选方案。

## 5. AI 与课程 RAG 的角色分工

**工作流决定阶段，学习者负责决策，LLM 负责发问与评审，课程 RAG 提供可追溯知识。**

- “何时问/何时停/允许几轮”由固定流程及校验规则控制，不交给 Agent 自行无限调用工具。
- 教学 Prompt 与检索 Query 应分离：先请求 1–3 条**英文**课程 Query，经选定检索策略获取课件，再带来源生成题目/反馈。
- 不把模型自己生成的参考答案再次当作课件知识；引用必须指向真实 Slide。
- 用户自行选择 `baseline`、`llm_assisted` 或 `hybrid`，整个案例开始后不随意改变策略，以免不同决策点的检索出处混杂。
- “准确找到课件页码”只能保证来源可追溯；模型的推理仍需由教学评价或人工评审确认。

## 6. 评审理念、限制与未来改进方向

**当前实现不使用固定百分制评分。** 没有经校准的人工 Rubric 数据，盲目输出“85/100”会制造虚假的客观性。现有输出包括学习总结、优点、改进和参考思路，可用于形成性评价。

后续若要做正式教学评估，应先：
1. 由课程教师对典型回答建立分项 Rubric、允许多个合理技术方案；
2. 区分首次独立正确、追问后修正、仍未解决三类表现；
3. 让同一题目在不同模型/检索策略下重复评测，检查评分一致性；
4. 加入人工盲评和“课件证据是否真正支持评价”的抽查；
5. 才考虑数值化能力评分或课程成绩。

明确不在当前学习主线内：完整 API 协议设计、代码实现测评、部署平台、多 Agent 运行时、正式成绩或作弊检测。
